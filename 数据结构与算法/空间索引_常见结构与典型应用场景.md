# 空间索引：常见结构与典型应用场景

## 1. 空间索引到底在解决什么问题

空间索引的核心目的不是替代精确几何计算，而是：

> **快速排除绝大多数“不可能相关”的空间对象，只留下少量候选对象，再进行精确计算。**

典型流程：

```text
大量空间对象
   ↓
空间索引粗筛
   ↓
少量候选对象
   ↓
精确几何判断
   ↓
最终结果
```

例如：

```text
附近 500 米自行车
→ 空间索引筛候选
→ 精确距离判断

鼠标 Picking
→ 空间索引筛候选对象/三角形
→ Ray-Triangle 精确求交

碰撞检测
→ 空间索引找可能碰撞对象
→ Narrow Phase 精确碰撞

GIS Polygon 查询
→ MBR 粗筛
→ Polygon-Polygon 精确相交
```

因此理解空间索引时，应该始终区分：

- **Broad Phase：粗筛**
- **Narrow Phase：精确判断**

# 2. Uniform Grid（规则网格 / 均匀网格）

## 名称

**Uniform Grid**

也常叫：

- Regular Grid
- Fixed Grid
- Uniform Spatial Grid

## 核心意义

把整个空间按固定大小切成完全相同的格子。

二维：

```text
+----+----+----+
|    |    |    |
+----+----+----+
|    |    |    |
+----+----+----+
|    |    |    |
+----+----+----+
```

三维则变成规则立方体网格。

## 最大特点

空间坐标可以直接计算格子下标，不需要从树根逐层查找。

例如：

```js
col = Math.floor(x / cellSize);
row = Math.floor(y / cellSize);
```

三维：

```js
ix = Math.floor(x / cellSize);
iy = Math.floor(y / cellSize);
iz = Math.floor(z / cellSize);
```

所以：

```text
空间坐标
↓
公式计算
↓
直接得到 Grid 下标
```

## 优点

- 结构极其简单
- 点定位很快
- 找邻近格子很容易
- 动态对象更新成本低
- 特别适合大量频繁移动对象

## 缺点

最难的问题是：**cellSize 怎么选？**

格子太大：

```text
一个格子里对象太多
→ 候选集太大
→ 粗筛效果差
```

格子太小：

```text
大对象跨很多格子
→ 重复记录
→ 更新成本增加
→ 查询需要去重
```

而且所有区域都使用相同分辨率，不适合空间密度差异非常大的数据。

## 典型场景

特别适合：

- 大量大小接近的动态物体
- 2D 游戏角色/NPC
- 车辆碰撞
- 粒子系统
- 小球碰撞
- 简单物理 Broad Phase
- 局部邻域查询

### 典型例子：小球碰撞

```text
100000 个小球
↓
根据小球位置直接算 Grid
↓
查询自己格子 + 周围格子
↓
得到几十个候选球
↓
精确 Sphere-Sphere / Circle-Circle 判断
```

# 3. Spatial Hash（空间哈希）

## 名称

**Spatial Hash / Spatial Hashing**

## 核心意义

可以理解为：

> **Uniform Grid + HashMap。**

Uniform Grid 如果世界特别大，直接创建完整三维数组非常浪费。

Spatial Hash 不创建所有格子，只存真正有对象的格子。

例如：

```text
cell(10,20,3)
↓
hash(10,20,3)
↓
HashMap
```

或者：

```js
map.get("10,20,3")
```

## 优点

- 保留 Uniform Grid 的快速定位能力
- 不需要为巨大空空间分配完整网格
- 非常适合稀疏大世界
- 动态更新简单

## 缺点

- 依然存在 cellSize 选择问题
- 大对象仍可能跨多个 cell
- 需要处理 hash 冲突/重复候选

## 典型场景

- 超大或近似无限世界
- 动态游戏对象
- 粒子邻域搜索
- 流体模拟
- 小球碰撞
- 大量稀疏对象

# 4. Quadtree（四叉树）

## 名称

**Quadtree**

## 核心意义

二维空间的递归自适应划分。

每次把一个区域分成 4 块：

```text
+-------+-------+
|  NW   |  NE   |
+-------+-------+
|  SW   |  SE   |
+-------+-------+
```

如果某个区域对象太多，就继续四分。

## 与 Uniform Grid 的本质区别

Uniform Grid：

```text
所有地方统一切
```

Quadtree：

```text
稀疏区域不继续切
密集区域继续细分
```

所以它是一种：

> **自适应空间分辨率。**

## 查询方式

不是先找到“用户所在叶子”，再找邻居。

通常是：

```text
queryBox
↓
从 Root 开始
↓
queryBox 和 node.boundingBox 相交？
↓
否：整个子树剪掉
是：继续往下
```

## 大对象问题

一个大对象可能跨多个子区域。

常见处理：

- 重复放入多个 child
- 或者如果不能完整放进某一个 child，就留在父节点

## 优点

- 数据分布不均时比 Uniform Grid 更自然
- 空间稀疏区域不会被过度细分
- 查询时可以大量剪枝

## 缺点

- 点定位不能像 Grid 那样直接 O(1) 算下标
- 动态对象移动时维护成本更高
- 大对象跨节点时处理复杂

## 典型场景

- 二维地图
- 地图 POI
- 2D GIS
- 2D 编辑器
- 二维碰撞管理
- 分布高度不均的二维对象
- 地图瓦片层次结构

## 一句话记忆

> **Grid 解决“快速定位”，Quadtree 解决“二维空间密度不均”。**

---

# 5. Octree（八叉树）

## 名称

**Octree**

## 核心意义

Quadtree 的三维版本。

每个节点把空间沿 X/Y/Z 同时切一半：

```text
2 × 2 × 2 = 8 个 child
```

它仍然属于：

> **先切空间，再把对象放进去。**

## 优点

- 三维空间层次结构清晰
- 非常适合空间占用数据
- 适合场景级对象管理
- 可以快速进行范围查询和剪枝

## 缺点

- 大三角形/大物体可能跨多个节点
- 规则空间切分可能产生大量空节点
- 对表面型三角网格，不一定比 BVH 紧致

## 典型场景

- 3D 场景管理
- Voxel / 体素
- 点云
- 空间占用查询
- 三维碰撞粗筛
- 场景级 Mesh 管理
- 稀疏三维数据

## 与 BVH 的直观区别

Octree：

```text
先有空间
↓
固定八分
↓
对象放进去
```

BVH：

```text
先有几何对象/三角形
↓
分组
↓
给每组生成紧致 BoundingBox
```

# 6. R-tree

## 名称

**R-tree**

R 一般可理解为 Rectangle。

## 核心意义

R-tree 不先把世界切成规则区域。

它的核心是：

> **把空间上相近的对象分成一组，并用一个 MBR（Minimum Bounding Rectangle，最小包围矩形）把这一组对象包起来。**

例如：

```text
A B C             D E F
```

可以组织成：

```text
             Root
           /      \
      Group1      Group2
      / | \        / | \
     A  B  C      D  E  F
```

Group1、Group2 都有自己的 MBR。

## 与 Quadtree 的本质区别

Quadtree：

> 先有空间区域，再放对象。

R-tree：

> 先有对象，再根据对象位置生成包围盒。

可以记成：

```text
Quadtree：空间驱动
R-tree：对象驱动
```

## 查询流程

```text
queryBox
↓
和 Root/Group MBR 判断相交
↓
不相交：整棵子树剪掉
↓
相交：继续进入 child
↓
到叶子后检查对象自己的 MBR
↓
得到候选对象
↓
真实几何精确判断
```

## R-tree 为什么重视 MBR 重叠

R-tree 的兄弟节点 MBR 可以相互重叠。

如果重叠太大：

```text
一个 query
↓
同时进入很多分支
↓
剪枝效果变差
```

所以构建 R-tree 时通常希望：

- MBR 面积尽量小
- 兄弟 MBR 尽量少重叠
- 空间相近对象尽量放在一起

## 插入思想

插入对象时，经常优先选择：

> **为了容纳新对象，BoundingBox 扩张最少的 child。**

节点满后会发生：

```text
split
```

然后可能向父节点继续传播。

## 优点

- 适合大小差异很大的空间对象
- 适合复杂 Polygon/LineString
- 很适合动态插入/删除的空间数据库
- 对 GIS 范围查询非常自然

## 缺点

- 建树和 split 策略比较复杂
- MBR overlap 会严重影响查询性能
- 真实 Polygon 查询仍需要精确几何判断

## 典型场景

- GIS
- 空间数据库
- 建筑物 Polygon
- 道路 LineString
- 地块查询
- 地图视窗范围查询
- `intersects / contains / within`

---

# 7. R*-tree

## 名称

**R*-tree**

## 核心意义

R-tree 的经典改进版本。

主要目标仍然是：

- 降低节点 MBR 重叠
- 减少 MBR 面积
- 改善 split 质量
- 必要时进行 reinsertion

## 典型场景

与 R-tree 基本一致：

- GIS
- 空间数据库
- Polygon/LineString 空间查询
- 多维范围查询

可以先理解为：

> **更重视树质量和查询性能的 R-tree。**

---

# 8. STR Tree（Sort-Tile-Recursive）

## 名称

**STR Tree / STR-packed R-tree**

全称：

**Sort-Tile-Recursive**

## 核心意义

当一批空间数据已经全部知道，并且数据基本静态时，不需要一个个动态 insert。

可以一次性排序、分组、批量构建高质量的 R-tree。

## 典型场景

- 静态 GIS 数据
- 批量加载 Polygon
- 空间几何库
- 需要大量查询、但很少动态修改的数据

## 一句话记忆

> **R-tree 偏动态插入；STR 更适合静态数据批量建树。**

---

# 9. BVH（Bounding Volume Hierarchy）

## 名称

**BVH — Bounding Volume Hierarchy**

中文常叫：

**包围体层次结构**

## 核心意义

把大量几何 primitive（典型是 Triangle）进行分组，每一组都用一个 Bounding Volume 包住。

例如：

```text
1,000,000 triangles
↓
              Root Box
             /        \
         Left Box    Right Box
          /   \        /   \
        ...   ...     ...   ...
                 ↓
               Leaf
                 ↓
          少量 Triangle
```

## 关键特点

BVH 不要求像 Octree 那样规则切空间。

典型二叉 BVH 每一层可以根据当前 Triangle 分布决定：

```text
沿 X 切
或
沿 Y 切
或
沿 Z 切
```

并且子节点 BoundingBox 是根据实际 primitive 重新计算出来的紧致包围盒，而不是父空间机械切出来的盒子。

## 构建过程

例如当前节点：

```text
10000 triangles
```

可能：

```text
Root：沿 X 分
Left：沿 Z 分
Right：沿 Y 分
```

最终直到叶子里只剩少量 Triangle。

## 为什么适合 Triangle Mesh

Triangle Mesh 往往是“表面型几何”：

- 建筑只有表面三角形
- 汽车内部大量空间为空
- 地形是接近二维的表面

BVH 可以紧贴实际几何分布建 BoundingBox，不需要切大量空空间。

## 查询方式

典型 Raycast：

```text
Ray
↓
Ray vs Root AABB
↓
不相交：剪枝
↓
相交：继续 child
↓
最终只剩少量 Triangle
↓
Ray-Triangle 精确求交
```

## SAH

高质量 BVH 常使用：

**SAH — Surface Area Heuristic**

核心是估算：

> 怎样切分，可以让未来 Ray 查询的平均成本更低？

不是简单永远沿最长轴切。

## 典型场景

- three.js Raycast 加速
- `three-mesh-bvh`
- 静态复杂 Mesh
- Ray Tracing
- Path Tracing
- Triangle Collision
- 复杂网格精确碰撞

## 与 Octree 的一句话区别

> **Octree 切空间，BVH 包几何。**

---

# 10. Dynamic AABB Tree / Dynamic BVH

## 名称

- **Dynamic AABB Tree**
- Dynamic BVH

## 核心意义

BVH 并不一定只能用于静态 Triangle。

还可以让叶子节点保存整个动态刚体/Object 的 AABB。

对象移动后，对树进行动态更新。

## 典型场景

- 2D/3D 物理引擎
- 刚体碰撞 Broad Phase
- 动态场景对象
- 游戏碰撞系统

## 一句话记忆

> **静态 Triangle 常用 BVH，动态刚体 Broad Phase 常见 Dynamic AABB Tree。**

---

# 11. KD-tree

## 名称

**KD-tree — k-dimensional tree**

## 核心意义

每一层选择一个维度，把点集分成两半。

例如 3D：

```text
Root：按 X 分
↓
下一层：按 Y 分
↓
下一层：按 Z 分
```

它非常适合“点数据”。

## 主要优势

特别擅长：

- 最近邻查询
- kNN
- 半径邻域查询

例如：

> 给定一个 3D 点，找离它最近的 10 个点。

## 典型场景

- 点云
- 最近邻
- kNN
- 摄影测量
- 机器学习中的空间点查询
- 几何处理

## 一句话记忆

> **如果问题核心是“点到点最近邻”，优先想到 KD-tree。**

---

# 12. BSP Tree（Binary Space Partitioning）

## 名称

**BSP Tree — Binary Space Partitioning Tree**

## 核心意义

使用一个平面把空间切成两半，再递归继续切。

与 Octree 不同：

- 不要求固定八分
- 分割平面可以不是固定轴对齐
- 可以使用任意方向平面

## 典型场景

- 早期 3D 游戏引擎
- 室内场景可见性
- CSG
- 几何布尔运算
- 空间前后关系

经典游戏/引擎历史中经常会看到 BSP。

---

# 13. Loose Quadtree / Loose Octree

## 名称

- Loose Quadtree
- Loose Octree

## 核心意义

普通 Quadtree/Octree 的问题之一：

> 大对象很容易跨节点。

Loose 版本让节点的实际可容纳空间比严格逻辑区域稍微大一些。

这样可以减少：

- 大对象跨多个节点
- 动态对象频繁换节点

## 典型场景

- 动态游戏对象
- 大小差异较大的 Mesh
- 游戏场景管理
- 3D/2D 动态空间查询

# 14. GPU Picking / ID Buffer —— 不是传统空间索引，但经常用于替代 Picking 查询

虽然它严格来说不是空间索引，但在 3D Picking 场景非常重要。

## 核心思想

给每个对象一个唯一 ID，并额外渲染一次 ID Pass：

```text
Object A → ID 1 → 唯一颜色/整数
Object B → ID 2
Object C → ID 3
```

点击屏幕 `(x, y)`：

```text
读取该像素
↓
得到 ID
↓
找到 Object
```

GPU 的 Depth Test 会自动解决遮挡关系。

## 优点

- 特别适合“屏幕上点中了哪个 Object”
- 不必逐对象做 CPU Raycast
- GPU 已经完成投影、裁剪、深度测试

## 缺点

- 需要额外 Picking Pass
- `readPixels` 可能造成 GPU→CPU 同步
- 如果需要 triangle、uv、normal、精确交点，往往还需要进一步 Raycast

## 常见组合

```text
GPU Picking
↓
得到 Object ID
↓
只对这个 Object 做 BVH Raycast
↓
得到 triangle / point / uv / normal
```

# 15. 常用空间索引快速对照表

| 空间索引 | 核心思想 | 典型数据 | 动态性 | 典型应用 |
|---|---|---|---|---|
| Uniform Grid | 固定大小均匀切空间 | 大量尺寸接近对象 | 很强 | 游戏角色、小球、动态碰撞 |
| Spatial Hash | Grid + HashMap | 稀疏动态对象 | 很强 | 大世界、粒子、流体、碰撞 |
| Quadtree | 二维递归四分 | 2D 空间对象 | 中等 | 地图、POI、2D GIS |
| Octree | 三维递归八分 | 3D 空间/体素 | 中等 | 3D 场景、体素、点云 |
| R-tree | 相近对象分组 + MBR | Polygon/Line/Object | 强 | GIS、空间数据库 |
| R*-tree | 改进 R-tree，降低 overlap | Polygon/Line/Object | 强 | 高质量 GIS 空间索引 |
| STR Tree | 静态批量构建 R-tree | 静态 GIS 几何 | 弱 | 批量 Polygon 查询 |
| BVH | primitive 分组 + 紧致包围体 | Triangle/Mesh | 静态最强 | Raycast、Ray Tracing、Mesh 碰撞 |
| Dynamic AABB Tree | 动态 BVH/AABB | 刚体/Object | 强 | 物理引擎 Broad Phase |
| KD-tree | 按维度二分点集 | Point | 静态较好 | 点云、最近邻、kNN |
| BSP Tree | 平面递归二分空间 | 空间/几何 | 较弱 | CSG、室内可见性、早期游戏 |
| Loose Quad/Octree | 放宽节点空间范围 | 大小混合对象 | 较强 | 动态游戏场景 |

# 16. 看到一个新问题时，怎么选空间索引

不要先问：

> 哪个空间索引最厉害？

应该先问下面几个问题。

## 1）数据是什么？

```text
Point？
Triangle？
Polygon？
整个 Mesh/Object？
Voxel？
```

## 2）二维还是三维？

```text
2D → Quadtree / Grid / R-tree
3D → Octree / BVH / Grid / KD-tree
```

## 3）对象会不会频繁移动？

```text
大量动态对象
→ Grid / Spatial Hash / Dynamic AABB Tree

静态 Triangle
→ BVH
```

## 4）空间分布均匀吗？

```text
比较均匀
→ Uniform Grid 很合适

非常不均匀
→ Quadtree / Octree / R-tree / BVH
```

## 5）对象尺寸差异大吗？

```text
尺寸接近
→ Grid 很舒服

尺寸差异巨大
→ R-tree / BVH / Loose Tree 往往更自然
```

## 6）查询类型是什么？

```text
附近有哪些对象
→ Grid / Quadtree / R-tree

Polygon 范围查询
→ R-tree

最近邻
→ KD-tree

Ray vs Triangle
→ BVH

动态碰撞 Broad Phase
→ Grid / Spatial Hash / Dynamic AABB Tree

3D 空间占用
→ Octree
```

# 17. 最终建立的判断直觉

可以先用下面这套快速联想：

```text
大量动态、尺寸接近
→ Uniform Grid / Spatial Hash

二维、数据密度不均
→ Quadtree

三维空间占用 / 体素
→ Octree

GIS Polygon / Road / Building
→ R-tree / R*-tree

静态 GIS 批量数据
→ STR Tree

点云最近邻
→ KD-tree

静态复杂 Mesh / Triangle
→ BVH

动态刚体 Broad Phase
→ Dynamic AABB Tree

CSG / 空间平面划分
→ BSP Tree
```

最重要的一句话：

> **空间索引没有绝对最优，只有是否适合当前的数据分布、对象尺寸、更新频率和查询类型。**

掌握这一点之后，再遇到新的空间索引结构，重点就不再是记名字，而是判断：

1. 它是在“切空间”还是“组织对象”；
2. 它的叶子节点里放什么；
3. 它的查询体是什么；
4. 它如何剪枝；
5. 它适合静态还是动态数据；
6. 它为哪类查询做了优化。

这就是理解空间索引最通用的一套思路。
